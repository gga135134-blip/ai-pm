## 2026-08-31 · 教训/红线库（项目①·让纠正开始复利）

**起因（用户原话）**：「AI 的能力每次都要我说，都要我改，花了很多时间去改。」

**诊断**：用户的每一次纠正都是**一次性消费，没有落点**。现有的库存的全是「要做什么」——人设条目、原料库、打法库、受众、锚点。**没有任何一张表存「不要做什么」**，而日常纠正 90% 都是「不要」。结果同一个毛病 AI 无限次重犯，用户无限次纠正。

这不是「范围没设好」：人设/受众/锚点/打法解决的是**方向**（说什么、对谁说），拦不住**手感**类错误（开头太软、书面语、讲太深）。用户仍在每天纠正，本身即是实证。

**意外发现**：`media_context.py:22` 的 `INJECTION_BUDGET` 里 **`"lesson": 3` 槽位当初就预留了**，注释写着「二期：只给 trigger_context 命中的」——连匹配策略都想好了，只是表没建、函数没写。这轮是**填自己挖的坑**，不是引入新概念。

merge `28f18e6`（8 提交，subagent 双审 + opus 整分支审 + 修复复审）。测试 380 → **425**。
spec: `docs/superpowers/specs/2026-08-31-media-lesson-memory-design.md`
plan: `docs/superpowers/plans/2026-08-31-media-lesson-memory.md`

### 1. 数据模型
新表 `media_lesson`，形状对齐 `media_playbook`。教训与红线**同表 `kind` 区分**（结构一样，差别只在强度：红线=绝对不许，教训=注意）。**按人设独享**（对齐宪法第 4 条，不加 `scope` 列）。`brief`（一句话，唯一进提示词的）/ `detail`（展开说明，只给人看）严格分离。`archived` 软删不硬删，保留证据链。

### 2. 写稿注入（核心取舍：红线与教训不共享配额）
`INJECTION_BUDGET` 加 `redline: 2`（`lesson: 3` 已有）。**红线单独占槽**——先例是记忆点 `signature`「绝不能被高置信度的普通条目挤掉」。若共享配额，存在「3 条高匹配教训占满、红线一条未进」的情形，红线失效。

- **红线不做匹配**：语义即「任何时候都不许」，做适用性判断自相矛盾。无条件带，按 `created_at` 取前 2。
- **教训做匹配**：`trigger_context` 与「标题+谜题+为什么做」算 bigram 重合度，**复用 `media_decision._overlap`** 不新造轮子（`media_decision` 只 import json，无循环依赖）。
- **插在提示词最末尾**、紧挨「请写出这条内容的口播脚本。」——近因效应，放开头会被前面一两千字的人设/素材/打法冲淡。**不放 `SCRIPT_SYSTEM`**：系统提示词写死在代码里，而红线按人设不同、会随时增删；放库里+末尾注入，页面上加一条下次写稿即生效。
- `mode == "lean"` 不注入（lean 语义就是只给身份行做对照）。
- **副作用（有意为之）**：红线上限 2 条，UI 提示「建议合并或降级为教训」——逼迫红线少而硬，一多就不值钱。

### 3. 可观测：hit_count
每条记被注入次数，**只在 AI 成功出稿后递增**（报错/费用保护/空返回都不计）。语义是「这条真的参与过一次成品生产吗」，不是「被拼进过几次提示词」。UI 标出 `hit_count == 0` 的条目 ⚠️ —— 那说明 `trigger_context` 写歪了或这条根本没必要存在。**配套给了编辑入口**：否则用户只能删了重建，`hit_count`/`created_at`/`evidence` 全丢，等于把观察窗口清零（这条是最终审抓出来的，原计划漏了）。

### 4. 两个产出入口
- **L2 复盘 advisory 接落点**：`L2_SYSTEM` 里原本白纸黑字写着「打法/教训/红线/权重调整建议 → advisory（**这些暂无自动落点，先当文字建议**）」——每轮花钱复盘出的洞见存进库就死在那儿，复盘页渲染出来给人看一眼，下游没有任何代码读它。现在结构化输出（brief + trigger_context + evidence）+ 复盘页加「采纳进本子」按钮。**归一化在读取侧兼容旧的纯字符串格式，不做数据迁移**；采纳走 `log_action` 留痕可撤、同 kind+brief 去重（strip 后比较）、已采纳显示灰态。
- **助手对话沉淀**（最值钱的一块）：用户随口一句「这个开头太软了，我们的人不吃铺垫」是几个月实战换来的判断，现在进 `media_assistant_message` 表、10 条滑动窗口后**永远蒸发**。新工具 `propose_lesson` 归 `_CORE`：只落 pending → 待确认卡 → 人点确认才写库 → 可撤。**撤销直接复用现成的 `created_table`/`created_id` 通用分支**，只在那个元组里加一个 `action_type`（宪法第 7 条：不另造撤销机制）。

**主动性取保守策略**：只在①用户正在跟它对话、②说的是否定性判断（不是普通改稿要求）、③它刚完成改动的那次回复里，顺带提议一次。一次只提一条、提完就停、绝不追问、**永远不主动发起会话**。拿不准时倾向不提——宁可漏记，不要吵。（跟项目③的定时心跳是完全不同的东西，本轮不涉及任何定时/主动推送。）这个度**上线后按手感调**，是 `MEDIA_ASSISTANT_SYSTEM` 里改一句话的事。

### 踩坑 / 教训
- **最终审抓到两条计划本身的疏漏**：①采纳没走动作日志（spec §5.2 明写要求留痕可撤，计划里写成了直接 `create_lesson`）②有 `update` 路由但模板没编辑入口，路由实际不可达。都是「spec 写了、计划漏了」，说明**计划自检要对着 spec 逐节核，不能只核自己写的任务**。
- **修复复审又抓到一个真缺口**：去重拿**未 strip 的 brief** 比对**已 strip 存库的 brief**，AI 文本带首尾空白时判重失效——正好漏在它本要堵的洞上。教训：**判重两边必须经过同一套规范化**。

#### 坑 1：计划里发明了一个不存在的 CSS class（最该记的一条）

模板里写了 `class="inp"`，但项目里的 class 叫 **`.input`**。全项目只有这一个文件用 `inp`，
所以那几个输入框是**完全没样式的裸 input**，inline-block 挤成一行、textarea 缩成小方块。

**三轮评审全没抓到**，原因是：
- 单元测试只验后端逻辑，不渲染页面
- subagent 冒烟用 **curl 打接口**——**HTTP 200 不等于页面能看**

**红线（已加进本子的那种）：UI 改动必须用眼睛验，不能用 curl。**
没有登录态时的替代办法：用 Jinja 离线把模板渲染成静态 HTML，再用浏览器打开看。
（`.input` 本身没有 `display`/`width`，别处都靠 `flex:1` 或包在 `.metric-field` 里撑开；
本子页要求每控件独占一行，所以加了页面局部类 `.lsn-f`。）

#### 坑 2：模板改了不用重启，Python 改了必须重启

Jinja 按文件 mtime 热重载，所以 `.html` 一 pull 下来刷新页面就是新的。
但 `.py` 是进程启动时加载的，**改了不重启就还在跑旧代码**——这就是历史上那个
"pull 了却一直跑旧代码"大坑的同一个家族。判断标准：本次 pull 有没有 `.py` 变更。

#### 坑 3：从腾讯云直连 GitHub 会**无声挂死**

`git pull origin main` 卡住，**一点输出都没有**（连 `Username for...` 都不弹）——
这是网络挂起，不是认证问题。十分钟前能通不代表现在能通。

- 诊断：`timeout 15 git ls-remote origin HEAD; echo $?`（124 = 超时）
- 可用镜像：`git pull https://ghfast.top/https://github.com/gga135134-blip/ai-pm.git main`
  （不改 `origin` 配置，是正经 fetch+merge，**不会造成工作区与 git 记录分叉**）
- 让它**失败而不是挂死**：`git config http.lowSpeedLimit 1000 && git config http.lowSpeedTime 20`

#### 坑 4：排查 HTTP 问题时日志里什么都看不到

- `journalctl -u ai-pm` **只有 systemd 的启停记录**，没有应用输出
- 应用日志在 `logs/app.log`，但**只记 WARNING 以上，没有访问日志**
- 所以「某个请求到没到、返回了什么」在日志里查不到

**替代诊断法（很好用，记住）**：绕过 HTTP 直接调 service 函数，一刀切开
「后端逻辑坏了」和「HTTP 层坏了」：
```bash
cd /www/wwwroot/ai-pm && PYTHONPATH=/www/wwwroot/ai-pm venv/bin/python /tmp/diag.py
```
⚠️ `PYTHONPATH` 不能省——`python /tmp/x.py` 会把 `sys.path[0]` 设成 `/tmp`，
找不到 `app` 包（`python -c` 则会带上当前目录，所以 `-c` 能跑、脚本文件不能跑）。

#### 坑 5：长请求在网络抖动时被断连，前端报得像后端崩了

写稿是几十秒的长请求。网络一抖连接被掐，前端 `await r.json()` 拿到**空 body**，
报 `SyntaxError: Unexpected end of JSON input`——**看着像后端崩了，其实后端好好的**。

判据：后端 `ok=True` 且 `logs/app.log` 里没有 `log.exception` 的记录 → 传输层问题。
当时用户终端也在反复 `* Reconnecting *`，是同一个网络问题。

**这不是本轮引入的**（写稿一直是长请求），但前端**没有重试也没有友好提示**，
撞上就是一句看不懂的 JS 报错。值得单独修一轮（加重试 / 区分"网络断了"和"后端错了"）。

#### 坑 6（我的）：从"表是空的"武断推出"你点了但没存进去"

空表跟「点了失败」和「压根没点」都吻合，从数据推不出是哪种。
**推不出来的别说死。** 后来验证表单其实是好的。

## 关键设计决策（贯穿始终的"宪法"）

1. **AI 注意力纪律（项目核心）**：任何往 prompt 堆信息的设计先过这关。"档案柜不是会议桌"——库只把**当前用得上的那一条**拿到桌上，绝不整库喂干活 AI。整库只能出现在**隔离的匹配调用**或**给人看的 UI** 里。
2. **人拍板**：AI 只提候选，绝不自动写库；人 adopt 才入。诚实不编造（只从真实来源挖，evidence 引原文）。
3. **取材范围按方法论分**：打法/素材**只从真爆款**抽（不爆的是噪音）；口头禅**从所有**老文案抽（腔调不看爆没爆）。
4. **共享边界**：打法库共享（方法论可迁移）；素材/人设独享（是"这个人是谁"）；原料库留 `scope` 接口备将来公司级共享。
5. **能复用别新建**：老文案 + 老视频统一走"反向补录已发内容"；批量挖复用现有 `mine_from_transcript`/`mine_structure`；采纳复用现有落库逻辑。
6. **分层人拍板**（对话助手落地）：查=免确认无痕；改草稿（选题/续集/脚本/整理格式）=AI 直接做但**留痕可撤**；核心动作（标爆款/删除/采纳入库/跑复盘）=**待确认卡**，点确认才执行、也留痕；**删除确认后不可撤**——确认卡就是它的安全闸。
7. **助手动作日志是通用留痕/撤销底座**（`media_assistant_action`）：任何"AI 改写/写库"类新功能，复用 `log_action` + 给 `revert_action` 加一个 `action_type` 分支即可，不另造撤销机制（老文案整理的 `organize_format` 就是这么接的）。
8. **长耗时批量走后台跑器**（复用 auto_runner 模式：模块级内存 `_jobs` + `asyncio.create_task` + Lock）+ 起/查端点 + 前端轮询；全局进度放 `_media_shell` 让任何媒体页可见（或就近放本页）；per-content/per-url 核心抽成 `run_*_one` 供单条端点和后台跑器共用。内存任务离页不断、服务器重启中断（做一条存一条，重跑剩下的）——持久化/续跑属 YAGNI 留后。（视频批量反向入库 `media_reverse_batch` 是这条的又一次落地：per-url 直接复用现成 `reverse_ingest`，进度就近放反向 tab。）
9. **归一化里"加分项因子"命中才计入分母**：像 `playbook` 这种多数样本无匹配的加分因子，只在真命中（`value>0`）时才进 `pos` 分母，不要恒 0 却常驻分母把整池绝对分稀释。有匹配纯加分、没匹配分数不变——比"永久进分母"更符合"辅助杠杆"语义，也不会让用户看到"分怎么整体低了"。
10. **AI 调用空响应要重试或如实报错，绝不装成功**：DeepSeek 等偶发返空（花了钱没吐字）。要么后台重试一次（费用累计、**只重试一次不死循环**），要么如实报错让用户重试——绝不把空当"完成"骗前端（诚信红线）。

13. **给一个流程加功能之前，先查它有没有被用**：2026-08-31 项目② brainstorm 差点直接开始
    包工具，追一句 SQL 才发现 97 条内容里正向写稿流程只跑通 7 条、可学样本 0——
    用户根本在 Claude 里写。**用量数据（谁在用、用了多少）是设计前的第一个检查项，不是最后一个。**
11. **UI 改动必须用眼睛验，不能用 curl**：`HTTP 200` 不等于页面能看。2026-08-31 本子页
    表单用了一个**不存在的 CSS class**（写成 `.inp`，项目里叫 `.input`），输入框全无样式挤成
    一行，**三轮评审全没抓到**——因为单测只验后端、冒烟只打接口。没有登录态时的替代办法：
    用 Jinja 把模板离线渲染成静态 HTML，浏览器打开看。
12. **改了什么决定要不要重启**：模板（`.html`）Jinja 按 mtime 热重载，pull 完刷新即生效；
    Python（`.py`）是进程启动时加载的，**不重启就还在跑旧代码**。这是历史上「pull 了却一直
    跑旧代码」大坑的同一家族，每次部署先看 `git diff --stat` 有没有 `.py`。

- **排查请求类问题时日志里看不到东西**：`journalctl -u ai-pm` 只有 systemd 启停记录；
  应用日志在 `logs/app.log` 但**只记 WARNING 以上、没有访问日志**。
  替代诊断法——**绕过 HTTP 直接调 service 函数**，一刀切开「后端逻辑坏了」vs「HTTP 层坏了」：
  `cd /www/wwwroot/ai-pm && PYTHONPATH=/www/wwwroot/ai-pm venv/bin/python /tmp/diag.py`
  （`PYTHONPATH` 不能省：`python /tmp/x.py` 会把 `sys.path[0]` 设成 `/tmp` 找不到 `app` 包；
  `python -c` 会带上当前目录所以能跑——这个差别坑过一次。）
- **腾讯云直连 GitHub 会无声挂死**（一点输出都没有，不是认证问题）。
  诊断 `timeout 15 git ls-remote origin HEAD; echo $?`（124=超时）。
  镜像可用：`git pull https://ghfast.top/https://github.com/gga135134-blip/ai-pm.git main`
  （正经 fetch+merge，不改 origin 配置，不会造成工作区分叉）。
  让它失败而不是挂死：`git config http.lowSpeedLimit 1000 && git config http.lowSpeedTime 20`。
